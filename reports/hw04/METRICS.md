## Why the speed-up grows with page size

The naive endpoint runs 1 query for the page plus 1 query per inspection, so its statement count grows linearly (12, 52, 202). The fixed endpoint uses `selectinload`, which loads all violations for the page in a single `WHERE inspection_id IN (...)` query, so it always runs 3 statements. At page size 10 both versions are dominated by fixed per-request cost (HTTP, session check, framework), so the gap is small. As the page grows, the naive version's per-row round trips become most of its latency while the fixed version barely changes, so the ratio keeps widening. 

## Index

Query: `SELECT id, restaurant_name, cuisine FROM inspections WHERE cuisine = 'Thai';`  
Index: 

```python
cuisine = Column(String(255), nullable=False, index=True)
```

EXPLAIN run in MySQL Workbench before and after creating the index.


| Index  | type | key                    | rows | filtered (%) |
| ------ | ---- | ---------------------- | ---- | ------------ |
| Before | ALL  | NULL                   | 5000 | 10           |
| After  | ref  | ix_inspections_cuisine | 496  | 100          |


Before the index, MySQL has to do a full table scan (`type = ALL`): it reads all 5,000 rows and expects only about 10% of them to match, so most of the rows it reads are thrown away. After the index, `type = ref` means MySQL looks up `'Thai'` in the index and goes straight to the matching rows. The estimate drops to 496 rows, and `filtered = 100` because every row found through the index already matches. A full scan grows with the size of the table, while the index lookup only grows with the number of matching rows. With index, the query run significantly faster. 

# HW4 Part 4 metrics

Corpus: 5 Markdown documents in `reports/hw04/corpus/` (FastAPI CORS, OAuth2/JWT, SQL databases; OWASP Session Management, Password Storage), 54 chunks.  
Chunking: `TokenTextSplitter(chunk_size=500, chunk_overlap=50)`. Embeddings: `all-MiniLM-L6-v2`, FAISS `IndexFlatIP` (score = cosine similarity).  
LLM: `qwen3:8b` via `src/model_client.py`, temperature 0. Run with `code/rag.py`, top_k = 3.

- (A) No RAG: question only.
- (B) Basic RAG: top-3 raw chunks + question.
- (C) Context-engineered RAG: drop chunks with score < 0.35 and near-duplicates (word Jaccard >= 0.8), order by score, label as `[n] (source, chunk_id)`, grounding rules (context only, cite `[n]`, refuse with "I cannot answer this question from the provided documents"). If no chunk survives, refuse without calling the LLM.

## Analysis

Retrieval worked for the questions whose wording matched one document. Q1 pulled two `cors.md` chunks, including the `max_age` line. Q2 got three chunks from the OWASP session cheat sheet: the timeout chunk ranked first, and the `HttpOnly; Secure; SameSite=Strict` sentence was in the third. Retrieval was only partly right for Q3 and Q4. For Q3, the Password Storage cheat sheet is about hashing from start to finish, so it filled every slot even at k = 5, and the short Argon2 section in FastAPI's `oauth2-jwt.md` never appeared. The answer was still correct, but the cross-document part was lost. For Q4, all three chunks were about session timeouts, so the CORS reading of "timeout" never reached the model.

The biggest improvement came from the grounding rules. With the same three chunks, B added facts from the model's own training: cookie `Domain` advice in Q2, a made-up "renew every 30 minutes" in Q4, and Django's real "2 weeks" default in Q5. Its accuracy was 0.83, but only 2 of its 5 non-refused answers were fully supported by the context. C used the same chunks, labelled them with source and chunk id, and told the model to cite and refuse. It answered all six questions correctly, with every claim cited, and each `[n]` could be traced back to a chunk_id.

The score filter helped on two questions. It removed an unrelated `sql-databases.md` chunk from Q1, so C's prompt was 1,021 input tokens against B's 1,388, even with the rules added. It dropped all three chunks for Q6 (top score 0.23), so C refused without calling the LLM. De-duplication never triggered: with 50-token overlap, neighbouring chunks share too few words to reach the 0.8 threshold. Chunk size stayed at 500 in all runs, so its effect was not tested.

On Q5 and Q6, the model hallucinated when it had no rules. Without RAG, it said Django sessions last 4 hours (wrong). B said 2 weeks, which is correct but not in the documents. On Q6, both A and B declined only because the question is subjective, not because of the missing evidence. C refused both questions with the exact required sentence. Q5 shows the limits of similarity scores: its chunks scored 0.44–0.47, close to Q1's 0.52, so the filter could not tell "on topic" from "contains the answer". The refusal came from the prompt, not from retrieval.

The k sweep shows more context is not always better. Q2 needed k = 3. At k = 1, C answered the cookie part from a passage about expiring cookies at logout. At k = 5, input tokens rose by about 60% with no gain. Q3 was already correct at k = 1, and k = 5 only made the answer longer and about 2x slower. Overall, retrieval decides what the model can know, the context decides what it sees, and the rules keep it inside that context.
